# Evaluation

## What is tested

`eval/queries.json` has **21 queries**:

- **12 standard**: different areas, space types, budget units, relative dates, explicit time ranges, must-have vs nice-to-have amenities.
- **9 messy or adversarial**:
  - a vague request
  - an impossible group size on a tiny budget
  - an area with no inventory (Juhu)
  - a city we don't serve (Pune)
  - a prompt injection asking for a free listing with a rooftop pool
  - Hinglish
  - heavy typos
  - contradictory preferences on an impossible budget
  - an off-topic request

Every query runs through the real `SearchService` with "now" fixed at **Mon 5 Oct 2026, 10:00 IST**, so "tomorrow" is reproducible. Checks are automatic (`eval/run_eval.py`):

1. **Outcome**: expected status (`ok` / `partial` / `no_exact_match` / `needs_clarification`), and for S1 the expected top listing.
2. **Parsing**: each expected field (area, group size, budget and unit, day, time, required vs preferred amenities, etc.) is compared with what the parser produced.
3. **Constraint correctness**: every *exact* result is re-checked against the hard constraints: area, capacity, space type, budget in the user's unit, required amenities.
4. **Grounding, on every query**: each returned listing must equal its dataset record exactly, and any LLM-written explanation must pass the grounding check.

**Rate limits are a real finding, not just an evaluation nuisance.** The first LLM run fell back to the rule parser on 15 of 21 queries. Only the first few queries succeeded before fallbacks began. That pattern matches Groq's free-tier limit for this model (8,000 tokens per minute) against the two LLM calls each search makes, but that run did not record fallback reasons, so the cause is inferred, not confirmed. The runner now paces queries, cools down and retries rate-limited queries, and records the fallback reason for every row.

For the product, the implication is concrete: on a free tier, only a couple of searches per minute get the LLM parser, and the rest silently get the rule parser. The fallback kept every search answering with 0 grounding violations, which is the design working as intended. But parse quality under load drops to the rule parser's level. Production needs a paid tier, caching (already in place for repeated queries), or dropping the LLM explanation call first when near the limit.

## Live end-to-end test (real server, LLM parser)

On 30 Sep 2026, around 22:25 IST, the app was used through its web UI on a running server with `openai/gpt-oss-20b`, typing requests a real booker might write, most of them outside the evaluation set. Relative dates resolved against the real clock ("tomorrow" = Thu 1 Oct).

**What held up:**
- The assignment's example query parsed fully, and the ranking matched the offline run.
- Heavy typos ("meetng room fr 6 ppl in bandraa tmrw mrng") parsed completely.
- The Hinglish query was understood.
- An unseen request ("client pitch in BKC this friday around 3pm, about 6 of us, must have a screen to show slides, budget 3k an hour") produced the right area, group size, day, time and must-have screen.
- A prompt injection asking for a free listing was refused, with no listing created.
- All LLM-written explanations passed the grounding check.

**What broke, and how it was fixed** (commit `b3afbb0`, each with a regression test in `tests/test_live_regressions.py`):

| Found live | Why it mattered | Fix |
|---|---|---|
| "on sunday" parsed as the calendar date 2026-10-01 (a Thursday) | The model doesn't know today's date, so it invented one and searched the wrong day | `reconcile.py`: a calendar date needs a date in the text; otherwise the weekday or relative day the user wrote is used |
| "max 1000 rupees total" and "1500 tak ka budget" read as per **day** | A per-day budget hides rooms that fit the real hourly budget | A per-day or per-person unit needs evidence in the text; otherwise total per hour, shown as an assumption. This also fixes S3, S6 and S12 from the first LLM run; S6 had doubled the budget |
| "with a whiteboard" treated as a must-have (S9) | Looked over-strict | **Deliberately kept.** Demoting must-haves was tried, but on the live server it reported a room without parking as a match for "anything with parking". An over-strict must-have is safer: when nothing has it, the no-match path shows the closest listings with the missing amenity stated. |
| "client pitch" → meeting room; "just me" → hot desk | An inferred space type hides valid cabins and desks | Space type is kept only if the user named one |
| "this morning" typed at 22:26 produced a 22:30–12:00 window and nonsense reasons | Any evening demo would hit this | A window that has passed today moves to tomorrow, with a note; today's slots never start in the past |
| A day without a time offered 24x7 spaces at 00:00–02:00 | Absurd suggestion | A day without a time searches working hours, 09:00–19:00 |

The rule behind all of these: **the LLM may relax nothing and tighten nothing the user didn't say.** Any hard constraint it adds without evidence in the text is relaxed and shown to the user as an assumption.

Caveat: some of these fixes also change results for queries in the evaluation set (S3, S6, S12). A re-run after them is therefore partly measured on the queries that motivated them. The unseen live queries above are the fairer check. The LLM results block records the code version it was measured on.

## What the evaluation does not cover

- **Ranking quality is only spot-checked** (S1's top result). There is no relevance judgement for positions 2–5; that needs human labels or booking data.
- **21 queries is small.** It is enough to find failure types, not to estimate an accuracy rate with any confidence.
- **The LLM run is non-deterministic** across provider-side model updates, even at temperature 0. Re-run it before quoting numbers.

## Automated tests

`pytest` runs 53 tests: unit, service, failure-mode and HTTP (`tests/test_api.py`). The LLM is mocked with `httpx.MockTransport` to exercise:

- malformed JSON
- a 429 followed by success
- strict schema rejected (falls back to JSON mode)
- 401
- timeout
- schema-invalid output with repair retry
- cache hits
- an LLM explanation that invents a feature (rejected, template used)
- the explanation call failing (template kept)
